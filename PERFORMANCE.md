# Производительность и готовность сервера

Дата: 13.10.2026. Цель — школьная платформа для 1100 учеников, примерно 120 учителей, сотрудников и родителей; рабочее допущение до 4000 аккаунтов. Это не заявленная пропускная способность.

## Уже выполнено

- Личные расписания используют снимок данных по версии пространства и адресу БД. Сохранение/отмена/повтор меняют версию и приводят к пересчёту при следующем обращении.
- Фактический день рассчитывается один раз для версии, затем выбираются строки конкретного ученика, родителя, учителя или другого разрешённого представления.
- Кэш ограничен двумя снимками, восемью датами и 128 недельными запросами на снимок. Возвращаемые строки копируются, поэтому изменение ответа не меняет кэш. Память зависит от размера школьного документа; замер RAM под длительной нагрузкой ещё необходим.
- Аккаунт и действующая сессия проверяются при каждом запросе. Права не кэшируются вместе с расписанием; посторонняя запись не выдаётся даже после прогрева кэша.
- SQLite-проверка авторизации вынесена из ASGI event loop в исполнитель синхронных операций. Чтение сессий и версии использует соединения только для чтения; проверка сессии не ждёт общий Python-замок записи и не выполняет DDL каждый раз.
- `/api/auth/status` повторно использует результат авторизации этого запроса.
- Разбор школьного JSON вынесен за пределы блокировки БД в обычном `read`. Соединения гарантированно закрываются после завершения контекста транзакции, включая откат.

Проверены шесть новых сценариев: повторное использование расчёта для разных пользователей, отсутствие изменения кэша вызывающим кодом, ограничение размера, смена версии и БД, сохранение/отмена и отзыв доступа, закрытие/откат соединений, отсутствие SQLite-вызова на потоке event loop. Всего **249 серверных тестов прошли**; изменения интерфейса в этом этапе не выполнялись.

## Воспроизводимый HTTP-замер

Из корня проекта:

```powershell
.venv/Scripts/python.exe -m tools.benchmark_portal --output data/feature-qa/portal-load.json --concurrency 20,100,300 --seconds 12
```

Скрипт создаёт временную БД только с синтетическими данными, запускает отдельный сервер на свободном порту `127.0.0.1`, использует заранее созданные сессии и останавливает именно этот процесс. `data/timetable.db` и школьные файлы не используются. На Windows учитывается дополнительный процесс, запускаемый Python из venv, и ожидается завершение перед удалением временной БД.

Набор: 1100 учеников, 2200 родительских аккаунтов, 120 учителей, 30 сотрудников, 55 классов, 2350 занятий и 34500 уведомлений. Всего 3450 аккаунтов. Это искусственные обычные классы, без полной сложности смешанных школьных групп.

Запросы: примерно 60% личное расписание дня, 10% доступные расписания, 20% уведомления, 10% состояние авторизации. Каждый поток немедленно отправляет следующий запрос после ответа. Значение «100» означает 100 одновременных HTTP-потоков, **не 100 человек, читающих страницу с паузами**. Аккаунты перебираются по мере выполнения, наличие всех 3450 записей в БД не означает одновременную активность каждого. Полный рабочий процесс учителей в журнале здесь не моделируется.

Клиент нагрузки и сервер работали на одном ноутбуке Windows 11, 28 логических CPU, около 16 ГБ физической RAM. Это короткие локальные прогоны, не отдельный выделенный сервер. Исходный прогон — по 10 секунд, итоговый — по 12 секунд плюс завершение начатых запросов. Другие нагрузки на ноутбуке дают разброс, поэтому цифры не являются серверной гарантией.

| Одновременных потоков | До: запросов/с | После: запросов/с | До: p95 | После: p95 |
|---|---:|---:|---:|---:|
| 20 | 30,97 | 123,71 | 756 мс | 316 мс |
| 100 | 28,12 | 107,23 | 5160 мс | 1269 мс |
| 300 | Не измерялось | 77,65 | Не измерялось | 9188 мс |

В итоговом прогоне 4053 ответа HTTP 200, без обнаруженных ошибок проекции чужого имени или включения составов учеников. Для p95 95% запросов завершились не позже указанного времени. Среднее время, p95 и число аккаунтов — разные показатели.

Первые промежуточные запуски обнаружили проблему очистки дочернего Python-процесса на Windows; она исправлена в инструменте. Итоговый прогон завершился с кодом 0. Отчёты сохранены локально в `data/feature-qa/portal-load-before.json` и `portal-load-verified.json`.

**Вывод:** чтение кабинетов ускорено, но при 300 непрерывных потоках видна перегрузка. Даже результат при 100 потоках пока не проходит предварительную цель p95 до 500 мс. Готовность школы на несколько тысяч аккаунтов не заявляется.

## Что измерять и менять дальше

1. Профилировать очереди потоков/блокировки, создание соединений, CPU/RAM и задержки диска на целевом сервере. Нынешний замер не определяет единственный источник перегрузки.
2. Убрать лишний опрос из скрытых вкладок, добавить сдвиг интервалов, объединение запросов и задержку повторов при ошибке. Действующий опрос уведомлений: каждые 25 секунд; сессия: каждую минуту. При 1000 активных вкладок только эти два потока дают примерно 57 запросов/с без пользовательских действий. Это расчёт по интервалам, а не измеренный трафик.
3. Подготовить PostgreSQL, миграции и пул соединений для расширения повседневных записей, не переписывая весь школьный документ при каждой оценке/сообщении. Журнал уже хранится отдельно от документа расписания. Переход БД сам по себе не исправит тяжёлые вычисления и не гарантирует ускорение.
4. Вынести генератор и тяжёлые задания из процесса API, ограничить ресурсы, обеспечить устойчивую очередь. Сейчас несколько API-процессов нельзя включать без решения координации заданий и состояния предложений.
5. Проверить полный учебный год журнала, массовую публикацию и раздачу уведомлений, одновременную запись 120 учителей, восстановление сессий и всплеск регистрации родителей. Нынешний тест не измеряет эти операции.
6. Отдельно проверить загрузку/выдачу файлов, размер клиентского пакета, сжатие и кэш статики, HTTPS, работу телефона по реальной сети.
7. Повторить тест на выбранном сервере с отдельным генератором нагрузки: ожидаемый сценарий с паузами, пиковый сценарий и длительный прогон. Критерии: задержки, ошибки, рост RAM/диска, сохранность данных и доступ к детям только у разрешённых аккаунтов.

## Обновление 14.10.2026

Пункты 2 и 4 продвинуты:

- Единый механизм опроса (`src/polling.ts`) приостанавливает скрытые/офлайн-вкладки, предотвращает перекрытие запросов одного опроса, объединяет принудительные повторы и увеличивает паузу при ошибках. Номинальные интервалы имеют случайный сдвиг ±10%. Скрытая вкладка продолжает получать уведомления только при явном включении браузерных уведомлений и наличии разрешения. Это не доставка при закрытом приложении и не общий координатор нескольких вкладок.
- Активный генератор опрашивается примерно каждые 1,5 секунды; без активного поиска — каждые 30 секунд. Присутствие и авторизация также используют паузу и повтор с задержкой.
- Основной решатель работает в отдельном процессе (`backend/solver_process.py`), по умолчанию до двух вычислительных потоков с пониженным приоритетом. Есть общий предел времени, кооперативная отмена и принудительное завершение зависшего поиска. Дочерний процесс не получает соединение с БД. Координация очереди и создание предпросмотра пока остаются в одном API-процессе; распределённая очередь и жёсткие лимиты RAM ещё не реализованы.

Проверки: **253 серверных и 28 клиентских тестов прошли**, производственная сборка успешна. Среди новых проверок — работа настоящего дочернего решателя, отмена до запуска и после запуска, завершение зависшего/упавшего процесса, отсутствие оставшихся дочерних процессов, границы числа потоков, пауза скрытой вкладки/сети, исключение для уведомлений, повтор после ошибок, отсутствие параллельного опроса и прекращение после закрытия компонента.

## Устойчивая очередь, 14.10.2026

Очередь генерации перенесена из памяти в отдельные таблицы БД. Параметры, отмена и число запусков сохраняются. Для одной локальной БД используется общий слот с уникальным токеном и сроком 15 секунд; исполнитель продлевает владение примерно раз в секунду. После остановки API задания восстанавливаются при запуске приложения без запроса из браузера. Истёкшее владение не может быть продлено старым исполнителем, а публикация результата дополнительно проверяет токен, отмену и исходную версию. Предпросмотр и статус записываются атомарно. Очередь ограничена тремя незавершёнными заданиями на пространство; один оборванный поиск запускается максимум три раза. Это перезапуск поиска, не восстановление внутренней позиции CP-SAT.

При простое координатор только читает БД; список последних 20 заданий читается одним запросом. Соединения явно закрываются и привязаны к конкретному файлу. Несколько координаторов одной БД проверены отдельными процессами, но это **не подтверждает многопроцессный запуск всей платформы**: другие виды поиска и временные состояния пока требуют прежнего ограничения в один API-процесс. Общая очередь между разными серверами, отдельная служба исполнителей и лимиты RAM остаются в плане.

Проверки: 271 серверный и 28 клиентских тестов, сборка. Добавлены конкурентная постановка с общим лимитом, конкуренция трёх процессов за один слот, продление/истечение владения, запрет записи старому исполнителю, сохранение отмены, предел повторов, устаревшие версии, обычная остановка и аварийное завершение, автоматическое восстановление через запуск приложения, миграция старых записей и привязка к исходной БД. В браузере на отдельной базе поиск дошёл до предпросмотра, на ширине 390 px нет горизонтального переполнения и ошибок консоли; результат не применялся.

`tools.verify_generation_recovery` проверил реальную аварийную остановку своего тестового API во время подготовки модели в дочернем процессе. Набор: 3451 аккаунт, 1100 учеников, 120 учителей, 2350 занятий; два поиска по 10 секунд. После перезапуска API оба задания получили статус `ready` за 25,12 секунды с учётом ожидания истечения владения: первый поиск запускался дважды, следующий — один раз. Созданы ровно два предпросмотра, исходный документ полностью совпал. Восстановление наблюдалось через БД без опроса API заданий. Итоговый прогон завершился кодом 0, временная БД удалена; первый промежуточный запуск выявил незакрытое соединение только в проверочном инструменте, оно исправлено. Отчёт: `data/feature-qa/queue-recovery.json`.

Повторный короткий сценарий чтения вместе с генерацией:

```powershell

Генератор завершился примерно за 5,7 секунды, результат не применялся; полный исходный документ остался прежним. Нагрузка перекрывала генерацию только первые 5,7 секунды. Данные относятся к 20 непрерывным потокам на этом ноутбуке, не доказывают ускорение вследствие новой очереди или готовность к 300–500 одновременно активным пользователям. Большие уровни нагрузки в этом этапе повторно не измерялись.

Воспроизводимая проверка на отдельной базе с 3451 синтетическим аккаунтом (1100 учеников, 2200 родителей, 120 учителей, 30 сотрудников и тестовый администратор):

```powershell

Для 55 опубликованных заданий 60 разных учеников выполняют по семь действий: открытие, сохранение черновика, загрузка TXT размером 256 КиБ, отправка, проверка назначенным учителем, чтение родителем и скачивание файла родителем. Одновременно выполняются до 20 сценариев без пауз пользователя. При HTTP 429 инструмент повторяет только загрузку с небольшой паузой; интерфейс приложения пока предлагает пользователю повторить её вручную. Тест проверяет принятие ответа, отсутствие черновика в родительском представлении, точное содержимое скачанного файла и неизменность полного расписания.

| Замер | Длительность всех 60 сценариев | p95 всех HTTP-попыток | HTTP 200 | HTTP 429 при загрузке |
|---|---:|---:|---:|---:|
| Повторный расчёт дня при каждом действии | 35,15 с | 2093,3 мс | 420 | 131 |
| Снимок расписания и кэш занятий дня по версии | 9,71 с | 704,5 мс | 420 | 57 |

После изменения p95 отправки — 480,7 мс, проверки — 491,5 мс, родительского чтения — 493,6 мс; скачивания — 1039,3 мс. Все сценарии завершились. HTTP 429 — срабатывание ограничения четырёх одновременных загрузок, поэтому считать весь поток ответами без отказов нельзя. Аккаунты, разрешения, публикация и версия работы не кэшируются; изменение версии расписания заменяет снимок, запись дополнительно проверяет актуальность внутри транзакции. Кэш ограничен двумя пространствами/базами и восемью днями в каждом снимке.

Клиент и сервер работали на одном ноутбуке. Это два локальных замера конкретного потока, а не приёмка сервера для всей школы. Большие файлы, массовый вход, генератор одновременно с этими записями, сеть/HTTPS, сотни одновременных участников и длительная нагрузка этим тестом не проверялись.

## Переписка и объявления — 14.10.2026

`python -m tools.benchmark_messages --output data/feature-qa/messages-load-final.json` создаёт отдельную синтетическую школу на 3451 аккаунт. Администратор публикует объявление 2200 родителям. Затем 60 семей при 20 одновременных сценариях создают личные диалоги, учителя отвечают, родители читают ответы, открывают входящие и подтверждают объявление. Проверяются два сообщения в каждом диалоге, отсутствие списка других семей у получателя, 60 подтверждений у автора и неизменность расписания.

Итог: 482 ответа HTTP 200; 60 семейных сценариев завершились за 7,18 секунды (отдельная отправка объявления и последующий отчёт автора находятся вне этого интервала). p95 создания диалога — 478,6 мс, ответа учителя — 620,9 мс, чтения ответа родителем — 558,8 мс, входящих — 452,8 мс, чтения объявления — 210,9 мс, подтверждения — 441,5 мс. Массовая отправка объявления заняла 228,1 мс, чтение отчёта о 2200 получателях — 458,2 мс; это одиночные измерения, не распределение p95.

Для диалога сервер читает аккаунты его участников, для списка — участников отобранной страницы. Чтение и подтверждение объявления получателем не загружает аккаунты других семей. Снимки расписания повторно используются до изменения версии; разрешения и актуальные аккаунты проверяются отдельно. Есть индексы участников/постов, постраничная история, ограничение частоты отправки, идемпотентность повторного запроса. Поиск в интерфейсе задерживается на 300 мс после ввода; постоянного опроса каждого диалога нет.

Замер проходил на ноутбуке с уже выданными сеансами, без пауз пользователя, файлов, массового входа, генератора, HTTPS и сетевой задержки. Он не доказывает готовность к школьному пику: чтение ответа родителем в этом прогоне превысило предварительную цель 500 мс. Нужны длительная нагрузка, больше активных пользователей, реальные сеть и сервер. Общие критерии из EDUPAGE_ROADMAP.md сохраняются.
