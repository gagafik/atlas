# «Атлас»: полная школьная платформа

Обновлено 15.10.2026. Пользователь расширил цель: аналог всей платформы EduPage, включая самостоятельную регистрацию родителей и работу школы на 1100 учеников, примерно 120 учителей и сотрудников. aSc Timetables остаётся одним из модулей.

## Как читать статусы

`Есть основа` означает работающий локальный сценарий, который ещё нужно довести до указанного объёма. `Нет` означает отсутствие рабочего модуля. Наличие пункта меню, модели данных или родственного сценария не считается завершённой функцией. Полная школьная эксплуатация пока не подтверждена.

Существующая [карта aSc](FEATURES.md) описывает расписание и некоторые общие возможности. Она **не является картой полного паритета с EduPage**. Этот документ расширяет объём. Каталог ниже охватывает основные модули официальной справки; детальные сценарии, региональные формы и варианты каждого модуля требуют отдельной приёмки.

Основания: [официальный каталог EduPage](https://www.edupage.org/), [справка по всем модулям](https://help.edupage.org/?lang_id=1). Статус нашей реализации определён по текущим API, моделям, интерфейсу и проверкам.

Наблюдения в рабочем EduPage школы (21.10.2026, только просмотр): масштаб, чем школа реально пользуется, и приоритетные пробелы — [EDUPAGE_SPEC.md](EDUPAGE_SPEC.md).

## Масштаб и критерии готовности

**14.10: чтение онлайн-тестов отделено от очереди записи.** Каталог, попытки,
история и параметры оценки используют снимки WAL. Истёкшие попытки завершаются
отдельной транзакцией с повторной проверкой прав и версий. На искусственном
сценарии завершены 100 работ при 50 одновременных участниках; целевые задержки
пока не достигнуты, некоторые p95 выросли. Метрики и ошибки сетевого стенда
зафиксированы в [PERFORMANCE.md](PERFORMANCE.md).

**14.10: уточнён способ измерения нагрузки.** Общий HTTP-клиент стенда добавлял
собственную очередь. Теперь сценарии по умолчанию используют отдельные клиенты,
а отчёт разделяет время до отправки, обработку API и остальные ожидания по каждой
операции. Это изменение измерителя, не ускорение приложения. Оба режима завершили
по 100 сценариев при 50 одновременно; запись оценки на сервере всё ещё превышает
целевую задержку. Ошибки закрытия соединений Windows остаются отдельной проблемой.

**15.10: ускорен выбор получателей уведомлений.** При записи оценки кандидаты
находятся по индексу учебных связей, который обновляется вместе с аккаунтами.
Действующие права и сроки родительских связей проверяются при каждой отправке.
На том же коротком сценарии 100 работ / 50 одновременно p95 записи оценки
снизился с 1817,5 до 1399,7 мс; цель 1 с ещё не достигнута. Подробности и
ограничения замера — в [PERFORMANCE.md](PERFORMANCE.md).

- 1100 учеников + 120 учителей + сотрудники + отдельные учётные записи родителей. Для проектирования: **до 4000 аккаунтов**, с возможностью увеличить лимит. Это рабочее допущение, не установленный предел.
- Один родитель может иметь нескольких детей; у ребёнка может быть несколько законных представителей. Число родителей нельзя автоматически считать равным числу учеников или удвоенному числу семей.
- Число зарегистрированных аккаунтов не равно числу одновременно работающих пользователей. Проверять сценарии 100, 300 и 500 активных пользователей с паузами между действиями; отдельно проверять всплеск входов и непрерывный поток запросов.
- Предварительная цель для обычного чтения API: p95 до 500 мс при ожидаемом рабочем пике; запись в журнал до 1 с, доля неожиданных ошибок менее 0,1%. Это **критерии будущей приёмки**, не текущие гарантии. Пользовательское время загрузки страницы измеряется отдельно на телефоне и через школьный интернет.
- Работа кабинетов во время генерации, публикации оценок и массового уведомления входит в обязательный тест.
- Проверить восстановление из копии на отдельном сервере, обновление с откатом и изоляцию доступа между семьями. Целевые сроки восстановления и допустимой потери данных утвердить до рабочего запуска.

## Регистрация родителей: согласованное направление

Родитель создаёт собственный аккаунт, подтверждает контакт и получает доступ к конкретному ребёнку после принятия одноразового школьного приглашения или проверки сотрудником. Одного имени/класса ребёнка недостаточно для выдачи доступа. Один аккаунт объединяет нескольких детей; несколько представителей получают отдельные аккаунты и отдельные разрешения. Повторное использование приглашения и одновременное принятие должны обрабатываться атомарно. Обязательны отзыв приглашения, срок действия, отсутствие перечисления учеников до подтверждения, журнал действий, ограничения попыток и восстановление доступа.

**14.10 реализован путь с локальной выдачей кода.** Администратор выбирает роль и конкретные записи, получает случайный код на 1–30 дней и передаёт его проверенному получателю. Код показывается один раз; БД хранит только его хеш. Получатель задаёт свои имя, логин и пароль. Уже зарегистрированный родитель может добавить ребёнка по следующему приглашению после проверки текущего пароля; старые сеансы завершаются. Повторное принятие, гонка принятия с отзывом, удаление школьной записи и изменение прав во время запроса проверены. Самостоятельная регистрация не меняет расписание.

Передача приглашения пока выполняется школой вручную; приложение не подтверждает email/телефон или полномочия законного представителя автоматически. Есть массовая подготовка и выдача кодов; провайдер доставки, подтверждение контактов и самостоятельное восстановление ещё впереди. Реестр семей позволяет сотруднику указать отношение, основание проверки и сроки; доступ отзывается отдельно для каждого ребёнка. Старое приглашение или обычная правка аккаунта не отменяет отзыв: восстановление выполняется явно через реестр. Пакеты и правила работы с кодами описаны в [INVITATIONS.md](INVITATIONS.md).

Проверка этого этапа: 262 серверных и 28 клиентских тестов, сборка; в браузере на отдельной синтетической БД пройдены выдача двух приглашений, регистрация родителя, добавление второго ребёнка и повторный вход. На ширине 390 px горизонтального переполнения нет; ошибок в консоли нет. Это проверка сценария, не нагрузочная приёмка регистрации всей школы.

## Порядок реализации

Уточнение владельца проекта, 15.10.2026: дополнение полного состава школы пока
отложено. С 23.10.2026 весь проект ведёт Claude: коллега, отвечавший за
расписание и журнал, и Codex больше не участвуют. Порядок ближайших работ и
способ их выполнения — в `WORK_PLAN.md`; список ниже остаётся общей картой.

1. **Основа эксплуатации:** профиль нагрузки, БД/миграции, отдельный исполнитель фоновых задач, файлы, наблюдаемость, резервирование и HTTPS. Начальный этап оптимизации кабинетов уже сделан, вся инфраструктура ещё не готова.
2. **Подключение школы:** реестр семей, самостоятельная регистрация по приглашениям, восстановление, права сотрудников, полный список учеников.
3. **Ежедневная работа:** сообщения/объявления, полный цикл домашних заданий, отсутствие и заявления родителей, итоговые оценки, фоновые уведомления.
4. **Учебный процесс:** планы/стандарты, материалы, тесты, результаты, интерактивные уроки и отчёты.
5. **Административные процессы:** встречи, формы/опросы, приём, платежи, столовая, библиотека/учебники, сотрудники, документы, архив и новый год.
6. **Остальные модули и интеграции:** публичный сайт, оборудование прохода, выдача ребёнка, дошкольные сценарии, закрытая поддержка ученика, AI и проверка каждого оставшегося сценария по каталогу.

Каждый этап завершается работающим сценарием, проверкой доступа, нагрузочным измерением для нового потока и возможностью восстановления данных. Число экранов и число пройденных тестов не являются процентом готовности всей платформы.
