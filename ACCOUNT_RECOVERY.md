# Самостоятельное восстановление доступа

Резервные коды позволяют восстановить пароль без почтового сервиса. Пользователь
должен создать и сохранить набор **до потери доступа**. Восстановления по email
или телефону и подтверждения контактов в этом модуле нет.

## Сценарий пользователя

1. После входа открыть «Резервные коды» рядом с управлением аккаунтом.
2. Подтвердить текущий пароль и создать восемь кодов. Каждый содержит 128 бит
   случайности, действует один раз; срок набора — 365 дней.
3. Скопировать или скачать коды и хранить отдельно от устройства входа.
   Они показываются только в ответе на создание. Закрытие окна удаляет их из
   состояния интерфейса; повторное открытие показывает только статус набора.
4. Если пароль забыт, выбрать «Забыли пароль?» на экране входа, указать логин,
   один сохранённый код и новый пароль длиной 12–128 символов. Регистр букв,
   пробелы и дефисы в коде несущественны. Пробелы пароля сохраняются.
5. После сброса войти с новым паролем. Все прежние сеансы аккаунта завершены.
   Использованный код больше не работает, остальные сохраняют исходный срок.

Создание нового набора сразу отзывает весь прежний. Для отзыва также нужен
текущий пароль. Обычная смена пароля, сброс администратором или через консоль,
смена логина/роли и отключение аккаунта отзывают коды. Последующее включение
аккаунта их не восстанавливает. Изменение имени и разрешений само по себе коды
не отзывает; восстановление всегда сохраняет текущие права, а не старые.

Если кодов нет, пользователь обращается к школьному администратору. Для владельца
сервера остаётся `python -m tools.reset_account_password <login>` с защищённым
вводом нового пароля. Код восстановления не используется как второй фактор
при обычном входе; это отдельное средство сброса пароля.

## Серверный контракт

- `GET /api/auth/recovery/options` — собственный статус, версия, остаток, срок и
  дата последнего использования. Все роли имеют одинаковый личный доступ.
- `POST /api/auth/recovery/codes` — `{version, currentPassword}`. Возвращает
  новый статус и `codes` только один раз. Чужой идентификатор указать нельзя.
- `POST /api/auth/recovery/revoke` — те же поля, отзыв собственного набора.
- `POST /api/auth/recover` — публичный `{login, code, password}`. Возвращает
  только `{status: "recovered"}`, удаляет cookie и не создаёт новый сеанс.

В БД хранятся SHA-256 от идентификатора аккаунта и случайного кода, состояние
набора, метки использования и привязка к текущему хешу пароля. Исходные коды
не записываются в аудит. Ответы API имеют `Cache-Control: no-store`;
ошибки валидации auth API не возвращают исходные значения полей.
Интерфейс не сохраняет коды в URL, localStorage или sessionStorage. Скачанный
файл и содержимое буфера обмена пользователь хранит самостоятельно.

Использование кода, смена пароля и отзыв сеансов выполняются одной транзакцией.
После дорогой проверки пароля/создания его хеша повторно проверяются учётная
запись, сеанс (для управления), актуальность набора и его версия. Один из
конкурирующих сбросов может завершиться отказом; неиспользованный код при этом
сохраняется. Чтение чужих кодов и повторная выдача исходных значений отсутствуют.

Неудачные попытки фиксируются **до** проверки секрета и не исчезают при отказе
или откате основной операции. Окно — 15 минут: восемь попыток на IP и логин,
40 суммарно на IP для восстановления; для управления — восемь на аккаунт и
120 суммарно на IP. Успешная операция снимает только собственную попытку.
Обычный вход использует отдельный счётчик. Неизвестный/отключённый аккаунт,
неверный, использованный, истёкший или отозванный код дают одинаковую ошибку.
Обратный прокси должен передавать проверенный адрес клиента по DEPLOYMENT.md.

После сетевого обрыва интерфейс не повторяет запись автоматически. Если ответ
на создание набора потерян, нужно выпустить новый набор. Если потерян ответ
на сброс, сначала проверить вход новым паролем; затем при необходимости
использовать оставшийся код.

## Копии и проверки

Полная SQLite-копия включает хеши, срок, остаток и историю использования кодов.
Тест восстановления копии проверяет отказ уже использованного кода и работу
оставшегося. Как и пароль, состояние кодов возвращается к моменту копии:
после восстановления старой копии нужно пересмотреть доступ и заменить наборы,
если с тех пор были сбросы или отзывы. Копии остаются закрытыми школьными данными.

`tests/test_recovery.py` проверяет роли, отсутствие исходных секретов в БД,
одноразовость, параллельные запросы, сроки и отзыв, изменение аккаунта во время
проверки, сохранение попыток, откат при ошибке аудита, CSRF, восстановление копии
и сохранение учебного документа. Все сценарии используют временную demo-БД.
Браузерный сценарий проверяется отдельно на искусственных аккаунтах; школьные
аккаунты или наборы кодов ради проверки не создаются.

Проверено 15.10.2026: 669 серверных тестов (30 новых для восстановления),
33 клиентских теста и сборка. На отдельной учебной БД в браузере пройдены
создание/замена/отзыв, восстановление и повторный вход, совпадение паролей,
одноразовый показ, скачивание и отсутствие кодов в браузерных хранилищах.
Задержанные ответы не возвращают старый статус; потеря ответа после создания
набора не вызывает автоматической повторной выдачи. Ширина 390 px без
горизонтального переполнения, ошибок в консоли нет. Запись в системный буфер
обмена тестовый браузер отклонил: проверено сообщение с предложением скачать
коды, успешная запись в буфер этим прогоном не подтверждена.

Экран восстановления и его стили загружаются отдельным файлом по запросу,
при обычном открытии кабинета этот код не загружается. Проверки модуля не
подтверждают производительность всей школы или доставку кодов через внешние сервисы.
