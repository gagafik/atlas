# Проверяемые резервные копии

Полная копия включает SQLite и все готовые частные вложения: домашние работы,
задания, сообщения, уведомления об отсутствии, учебные материалы и фото находок. Загрузки,
которые ещё не закончились, исключаются только из копии. Исходная база не меняется.

Копии содержат персональные данные, аккаунты и ключи. Они остаются в закрытом
хранилище, вне Git, образа приложения, статического сайта и журналов CI.

## Ручная копия и проверка

```sh
python -m tools.backup_school --database /app/data/timetable.db --output /private-backups/new-copy
python -m tools.restore_school /private-backups/new-copy
python -m tools.restore_school /private-backups/new-copy --output /private-restore/new-drill
```

На Windows используйте Python из `.venv/Scripts/python.exe`.
Для защищённой проверки требуется SQLite 3.42 или новее в составе Python;
версия видна через `python -c "import sqlite3; print(sqlite3.sqlite_version)"`.
Серверный образ использует Debian Trixie: прежняя SQLite 3.40.1 в Bookworm
отвергала существующий JSON-индекс при `trusted_schema=OFF`. Проверка остаётся
защищённой, старый runtime выдаёт требование обновления.

Выходной каталог должен быть новым: существующий не перезаписывается. Без `--output` последняя
команда только проверяет копию. Успех печатается после проверки всех файлов,
контрольных сумм, целостности SQLite, внешних ключей, ссылок на готовые вложения
и чтения JSON-документов пространств. Лишние/пропавшие файлы, символьные ссылки,
junction и выход путей за каталог отвергаются. Поддержаны имена базы с расширением
`.db`, `.sqlite`, `.sqlite3` и формат `atlas-local-backup-v1` прежних ручных копий.

`manifest.json` — признак законченного копирования; результат отдельной проверки
сильнее одного наличия этого файла. Контрольные суммы выявляют повреждение,
но не удостоверяют происхождение: используйте собственные доверенные копии.
Пробное восстановление не запускает сервер, рассылки или фоновые школьные задания.

## Автоматический цикл

Служба по умолчанию выключена. В серверном `.env` задайте:

```dotenv
ATLAS_BACKUP_DIR=/app/backups
ATLAS_BACKUP_INTERVAL_HOURS=24
ATLAS_BACKUP_KEEP=7
ATLAS_BACKUP_SNAPSHOT_TIMEOUT_SECONDS=30
ATLAS_BACKUP_VERIFY_TIMEOUT_SECONDS=600
```

```sh
docker compose --profile backups up -d --build
docker compose --profile backups ps
```

Отдельный контейнер `backups` использует тот же образ и том школы, а результаты
хранит в отдельном постоянном томе `atlas_backups`. Первый запуск создаёт копию
сразу; затем интервал отсчитывается от успешного завершения. Это интервал в часах,
не расписание «каждую ночь в 02:00». Допустимы 1–168 часов и 2–90 сохраняемых копий.
После ошибки повтор — через 15 минут; после остановки служба догоняет пропущенный
запуск. Для однократного принудительного цикла остановите службу, затем выполните:

```sh
docker compose --profile backups stop backups
docker compose --profile backups run --rm --no-deps backups python -m tools.backup_service --once
docker compose --profile backups up -d backups
```

Один worker владеет блокировкой для одной базы; второй экземпляр откажется
работать одновременно. Вне Docker задайте те же переменные окружения и запустите
`python -m tools.backup_service` через системный менеджер служб. Сам worker не
устанавливает автозапуск операционной системы. Новый каталог назначения должен
быть пустым; worker помечает его владельца и не принимает чужой каталог копий.
Для смены каталога назначения остановите worker и сохраните прежний каталог
`<имя базы>.backup-agent` отдельно; новый worker создаст новую историю.

Цикл:

1. Проверяет запас места: консервативно три объёма базы/вложений плюс 256 МиБ на
   каждом задействованном диске. Это предварительная оценка, не квота файловой системы.
2. Создаёт согласованный снимок в закрытой локальной папке рядом с базой.
   Во время снимка SQLite допускает чтение, но резервирует запись. Запись с
   истёкшим ожиданием возвращает HTTP 503 и предложение повторить действие.
3. Освобождает резервирование, проверяет и копирует снимок в хранилище.
4. Восстанавливает результат в новую временную папку и повторяет проверку.
5. Фиксирует успех и только затем удаляет старые собственные копии сверх лимита.

Фаза снимка ограничена 30 секундами, проверка/перенос/восстановление — 600 секундами.
Пределы настраиваются; повышайте предел снимка только после замера задержки записи.
Родитель завершает зависший дочерний процесс, у ребёнка также есть собственный
таймер на случай аварии родителя. После жёсткой аварии перезапуск ждёт истечения
сохранённого предела дочернего процесса: до этого служба отказывается начинать
новый цикл. Docker повторяет запуск согласно restart policy.

Незаконченные каталоги текущего записанного запуска очищаются. Ранее успешная
копия сохраняется при ошибке нового цикла. Если старая копия изменена вручную,
очистка останавливается и показывает предупреждение; не исправляйте историю
worker вручную. История и блокировка находятся в `<имя базы>.backup-agent`,
не входят в школьную резервную копию и исключены из Git/образа.

## Что видит администратор

Кнопка **«Состояние сервера»** показывает доступность базы, состояние worker,
последний успех, объём, количество вложений, длительность снимка, резервирования
записи и всего цикла,
результат пробного восстановления, ошибки и задержку следующей копии. Окно
обновляется каждые 10 секунд, при скрытой вкладке опрос приостанавливается.
Остановка/потеря worker определяется по отсутствию heartbeat более 30 секунд.
Ручные копии не входят в эту историю. Запуск и настройка службы выполняются
ответственным за сервер; кнопки восстановления рабочей школы в интерфейсе нет.

`/api/health` проверяет, что API отвечает. `/api/ready` выполняет ограниченное
чтение схемы/базы и в серверном режиме проверяет активного администратора.
Эти адреса не раскрывают школьные данные и не создают отсутствующую базу.
Docker healthcheck использует readiness. HTTP 200 не является полной проверкой
целостности, наличия свежей копии или готовности всей школы к нагрузке.
Сбой копирования виден отдельно и не вызывает бессмысленных перезапусков API.

## Восстановление после аварии

Сначала восстановите проверенную копию **в новый закрытый каталог**. Проверьте
вход, нужные школьные документы и скачивание закрытых вложений на изолированном
экземпляре с выключенной внешней доставкой. Проверка файлов/SQLite не заменяет
приёмку школьных сценариев. Не открывайте тестовое восстановление всем пользователям.

Для замены рабочей школы остановите API, worker копий и остальные фоновые
процессы. Сохраните прежнюю базу вместе с вложениями отдельно. Переносите базу
и соответствующую папку `<имя базы>.files` как единый набор, проверьте владельца
и права доступа. Не накладывайте файлы новой базы на старые WAL/SHM.
Порядок восстановления Web Push и предотвращения повторной доставки описан в
[PUSH_NOTIFICATIONS.md](PUSH_NOTIFICATIONS.md). Сессии и права восстанавливаются
на момент копии: перед открытием доступа проверьте актуальные аккаунты и отозванные
доступы. Автоматической замены рабочей базы команда восстановления не делает.

## Что ещё требует реального сервера

Отдельный Docker-том на той же машине **не защищает от потери машины**. Настройте
защищённое внешнее хранилище/резервирование тома и проверьте восстановление с него
на другом сервере. Путь `ATLAS_BACKUP_DIR` может указывать на заранее смонтированное
закрытое хранилище, но подключение, шифрование, контроль доступности и защита от
удаления на стороне этого хранилища настраиваются отдельно. В Compose произвольный
путь должен быть явно смонтирован; иначе копии попадут в слой контейнера.

Пока нет внешнего оповещения оператора о сбое, фиксированного ежедневного времени,
неизменяемых внешних копий и согласованных со школой сроков восстановления/потери
данных. Нужен замер на целевом сервере с реальным объёмом вложений и рабочей нагрузкой.
